AI Actions — config-editing UX mockups

Three directions for redesigning the action-management experience. Click into each to see it. All three share the plugin's existing color palette so the chrome looks the way it would in Logseq.

Mockup A

Native sidebar with live preview

Move the editor into Logseq's right sidebar so users can edit and test against the cursor's block in real time. Auto-save replaces the staged-and-commit flow.

storage: userActionsJsoncost: medium
Mockup B

Actions are blocks

Stop hiding actions in JSON. Each action is a real Logseq block tagged #ai-action, edited the way users edit anything else. Plugin watches DB for changes.

storage: graph blockscost: medium-high
Mockup C

Action gallery (refined modal)

Stay in the modal, refine the layout. Card grid, search, inline editor expansion, bigger prompt area with a char counter and variable-insert helper.

Mockup C — CRUD states (chosen direction)

Each card below is a different state of the same modal — what the user sees in different CRUD scenarios.

Read

Gallery + edit

The default landing view: cards for built-ins and user actions. Click a user action to expand the inline editor (also in this file).
Read · first-run

Empty state

What a brand-new user sees: built-ins shown, "Your actions" section is an empty-state CTA with three onramps (Create, Import, Read the guide).
Create

New action

Empty form variant of the editor. Same shape as Update so users only learn one form. Output mode and scope have sensible defaults.
Read · built-in

View built-in (read-only)

Inspecting a built-in shows the prompt with all fields disabled, plus a banner explaining read-only and offering "Duplicate as user action".
Update · errors

Validation errors

What an invalid edit looks like: error summary at top, per-field red borders + error messages, Save button disabled until fixed.
Delete

Delete confirmation

Modal-over-modal confirm. Names the action being deleted and explains the slash/palette consequence (no deregister API in Logseq).
